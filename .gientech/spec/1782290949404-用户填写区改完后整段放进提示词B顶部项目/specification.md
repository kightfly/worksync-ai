# 需求规格文档 - 勤务时间管理 App（企业版）

## 1. 引言

### 1.1 功能概述

构建一个日文界面的「勤务时间管理」React 全栈系统，面向企业用户，提供完整的出勤管理、工时统计、GPS 定位、审批流程及报表分析功能。系统用于练习 AI Agent 在约束下的可靠交付能力。

### 1.2 背景与目标

- **背景**：企业需要对员工勤务时间进行精确管理，包括出勤/退勤记录、休息时间、加班管理，并需要 GPS 定位验证工作地点，支持与薪酬/人事系统集成。
- **目标**：提供一个可靠、可扩展的勤务管理系统，支持多角色协作、数据分析和外部集成。
- **预期价值**：减少人工考勤管理成本，提高数据准确性，支持合规性审计。

### 1.3 关键利益相关者与用户

| 角色 | 职责 | 核心需求 |
|------|------|----------|
| 员工（従業員） | 日常打卡、查看工时 | 快速打卡、准确记录、工时查询 |
| 管理者（マネージャー） | 审批加班/请假、查看团队报表 | 审批流程、团队工时分析 |
| HR/人事（人事） | 薪酬计算、数据导出 | 数据导出、系统集成、报表分析 |
| 系统管理员（管理者） | 用户管理、系统配置 | 用户权限、系统设置 |

### 1.4 UI/UX 要求

- **界面语言**：日本語（前端所有 UI 文本）
- **开发对话语言**：中文（zh-CN）
- **时区**：Asia/Tokyo（UTC+9）
- **响应式设计**：支持桌面端和移动端

## 2. 需求

### 2.1 用户管理

#### 需求 [UM-001]

**用户故事**：作为一名员工，我希望通过邮箱和密码登录系统，以便访问我的勤务记录和任务。

**验收标准（EARS 格式）**：
1. 当用户输入有效邮箱和正确密码时，系统应成功登录并跳转到任务列表页
2. 如果邮箱格式无效，系统应显示"メールアドレスの形式が正しくありません"错误提示
3. 如果密码长度少于 6 位，系统应显示"パスワードは 6 文字以上で入力してください"错误提示
4. 系统应在登录成功后存储认证令牌（JWT）

#### 需求 [UM-002]

**用户故事**：作为一名用户，我希望能够登出系统，以便保护我的账户安全。

**验收标准（EARS 格式）**：
1. 当用户点击登出按钮时，系统应清除本地认证状态并跳转到登录页
2. 系统应在登出后使之前的认证令牌失效

#### 需求 [UM-003]

**用户故事**：作为一名管理员，我希望管理用户账户，以便控制系统访问权限。

**验收标准（EARS 格式）**：
1. 当管理员创建新用户时，系统应要求填写邮箱、姓名、角色和初始密码
2. 如果邮箱已存在，系统应显示"このメールアドレスは既に登録されています"错误提示
3. 系统应支持激活/停用用户账户
4. 系统应支持为用户分配角色（员工/管理者/HR/管理员）

### 2.2 核心功能 - 出勤管理

#### 需求 [AM-001]

**用户故事**：作为一名员工，我希望记录出勤和退勤时间，以便准确追踪我的工作时长。

**验收标准（EARS 格式）**：
1. 当用户点击"出勤打刻"按钮时，系统应记录当前时间为出勤时间，并获取 GPS 位置
2. 当用户点击"退勤打刻"按钮时，系统应记录当前时间为退勤时间，并计算当日工作时长
3. 如果用户未出勤尝试退勤，系统应显示"出勤していません"错误提示
4. 系统应支持手动修正打卡时间（需管理员审批）

#### 需求 [AM-002]

**用户故事**：作为一名员工，我希望记录休息时间，以便准确计算净工作时长。

**验收标准（EARS 格式）**：
1. 当用户点击"休憩開始"按钮时，系统应记录休息开始时间
2. 当用户点击"休憩終了"按钮时，系统应记录休息结束时间并计算休息时长
3. 系统应支持一天内多次休息记录
4. 系统应自动从工作时长中扣除休息时间

#### 需求 [AM-003]

**用户故事**：作为一名员工，我希望申请加班，以便记录额外工作时间。

**验收标准（EARS 格式）**：
1. 当用户提交加班申请时，系统应要求填写加班日期、开始时间、结束时间和理由
2. 如果加班申请超过当日退勤时间，系统应显示警告提示
3. 系统应将加班申请发送给管理者审批
4. 系统应在审批通过后更新工时统计

#### 需求 [AM-004]

**用户故事**：作为一名员工，我希望申请请假，以便记录缺勤情况。

**验收标准（EARS 格式）**：
1. 当用户提交请假申请时，系统应要求填写请假类型、日期范围和理由
2. 系统应支持请假类型：年次有給休暇、病気休暇、特別休暇、その他
3. 系统应将请假申请发送给管理者审批
4. 系统应在审批通过后更新出勤日历

### 2.3 GPS 定位功能

#### 需求 [GPS-001]

**用户故事**：作为一名员工，我希望在打卡时自动记录位置，以便验证工作地点。

**验收标准（EARS 格式）**：
1. 当用户进行出勤/退勤打卡时，系统应自动获取当前 GPS 坐标（纬度、经度）
2. 如果 GPS 获取失败，系统应允许用户手动选择工作地点或稍后重试
3. 系统应将 GPS 数据与打卡记录关联存储
4. 系统应在地图上显示打卡位置

#### 需求 [GPS-002]

**用户故事**：作为一名管理员，我希望设置有效工作区域，以便验证打卡位置的有效性。

**验收标准（EARS 格式）**：
1. 当管理员配置工作地点时，系统应支持设置中心坐标和有效半径（米）
2. 如果用户打卡位置超出有效范围，系统应标记为"範囲外"并通知管理者
3. 系统应支持多个工作地点配置
4. 系统应记录位置验证结果

---

### 2.4 审批流程

#### 需求 [AP-001]

**用户故事**：作为一名管理者，我希望审批员工的加班/请假申请，以便管理团队勤务。

**验收标准（EARS 格式）**：
1. 当有待审批申请时，系统应在管理者仪表板显示待办数量
2. 当管理者审批申请时，系统应支持"承認"和"却下"操作
3. 如果申请被却下，系统应要求填写却下理由并通知申请人
4. 系统应记录审批历史（审批人、时间、结果）

#### 需求 [AP-002]

**用户故事**：作为一名员工，我希望查看我的申请状态，以便了解审批进度。

**验收标准（EARS 格式）**：
1. 系统应以列表形式显示用户的所有申请记录
2. 系统应用不同状态标识：承認待ち/承認済み/却下済み
3. 当申请状态变更时，系统应通知用户（站内消息或邮件）

---

### 2.5 报表分析

#### 需求 [RP-001]

**用户故事**：作为一名员工，我希望查看我的工时统计，以便了解我的工作时长。

**验收标准（EARS 格式）**：
1. 系统应按日/周/月显示工时统计
2. 系统应显示：出勤时间、退勤时间、休息时长、加班时长、净工作时长
3. 系统应支持日期范围筛选
4. 系统应以图表形式展示趋势（柱状图、折线图）

#### 需求 [RP-002]

**用户故事**：作为一名管理者，我希望查看团队工时报表，以便分析团队工作效率。

**验收标准（EARS 格式）**：
1. 系统应显示团队所有成员的工时汇总
2. 系统应支持按部门/项目筛选
3. 系统应计算团队平均工时、加班率等指标
4. 系统应支持导出为 CSV/Excel 格式

#### 需求 [RP-003]

**用户故事**：作为一名 HR，我希望导出勤务数据，以便进行薪酬计算。

**验收标准（EARS 格式）**：
1. 系统应支持导出指定期间的所有勤务数据
2. 导出格式应包含：员工 ID、姓名、日期、出勤时间、退勤时间、休息时长、加班时长
3. 系统应支持 CSV 和 Excel 格式导出
4. 系统应记录导出历史（导出人、时间、范围）

---

### 2.6 数据管理

#### 需求 [DM-001]

**用户故事**：作为系统，我需要安全存储所有勤务数据，以便保证数据完整性和可追溯性。

**验收标准（EARS 格式）**：
1. 系统应将所有时间戳以 UTC 格式存储到数据库
2. 系统应在前端展示时转换为 Asia/Tokyo 时区（UTC+9）
3. 系统应对所有勤务修改记录审计日志（修改人、时间、原值、新值）
4. 系统应定期备份数据

#### 需求 [DM-002]

**用户故事**：作为系统，我需要与外部系统集成，以便数据同步。

**验收标准（EARS 格式）**：
1. 系统应提供 REST API 供外部系统调用
2. 系统应支持 Webhook 通知（勤务变更、审批完成等事件）
3. 系统应支持与薪酬系统的数据对接（按月导出）
4. 系统应支持与人事系统的员工数据同步

---

### 2.7 安全

#### 需求 [SC-001]

**用户故事**：作为系统，我需要保护用户数据和防止未授权访问。

**验收标准（EARS 格式）**：
1. 系统应对所有密码进行 bcrypt 加密存储
2. 系统应使用 JWT 进行 API 认证，令牌有效期为 24 小时
3. 系统应对所有 API 请求进行速率限制（100 次/分钟）
4. 系统应防止 SQL 注入、XSS、CSRF 攻击

#### 需求 [SC-002]

**用户故事**：作为系统，我需要基于角色的访问控制，以便限制用户操作范围。

**验收标准（EARS 格式）**：
1. 系统应定义角色：従業員、マネージャー、人事、管理者
2. 员工角色只能查看/修改自己的数据
3. 管理者角色可以查看下属数据并审批申请
4. HR 角色可以导出全公司数据
5. 管理员角色可以管理用户和系统配置

---

### 2.8 性能

#### 需求 [PF-001]

**用户故事**：作为用户，我希望系统响应迅速，以便高效工作。

**验收标准（EARS 格式）**：
1. 系统应在 2 秒内完成页面加载
2. 系统应在 500ms 内完成 API 响应（95% 请求）
3. 系统应支持并发 1000+ 用户访问
4. 系统应在 10 秒内生成月度报表

---

### 2.9 错误处理

#### 需求 [EH-001]

**用户故事**：作为用户，我希望在遇到问题时获得清晰的错误提示，以便了解如何解决问题。

**验收标准（EARS 格式）**：
1. 系统应对所有错误进行统一处理并返回友好提示
2. 系统应记录所有错误到日志系统（包含堆栈跟踪）
3. 系统应对网络错误进行重试（最多 3 次）
4. 系统应在服务器错误时显示"システムエラーが発生しました。管理者にお問い合わせください"

---

### 2.10 用户体验

#### 需求 [UX-001]

**用户故事**：作为用户，我希望界面直观易用，以便快速完成操作。

**验收标准（EARS 格式）**：
1. 系统应在主界面显示今日勤务状态（未出勤/出勤中/已退勤）
2. 系统应提供一键打卡功能（出勤/退勤）
3. 系统应在关键操作前显示确认对话框
4. 系统应支持深色/浅色主题切换

## 3. 数据模型需求

### 3.1 核心实体

| 实体 | 描述 | 主要字段 |
|------|------|----------|
| User | 用户账户 | id, email, password_hash, name, role, is_active |
| Attendance | 勤务记录 | id, user_id, work_date, check_in_time, check_out_time, break_duration, overtime_duration, gps_data |
| OvertimeRequest | 加班申请 | id, user_id, request_date, start_time, end_time, reason, status, approver_id |
| LeaveRequest | 请假申请 | id, user_id, leave_type, start_date, end_date, reason, status, approver_id |
| Approval | 审批记录 | id, request_id, approver_id, status, comment, decided_at |
| WorkLocation | 工作地点 | id, name, latitude, longitude, radius_meters |
| Report | 报表 | id, user_id, report_type, period_start, period_end, data, exported_at |

## 4. 非功能需求

### 4.1 技术约束

- **前端框架**：React 19 + TypeScript + Vite
- **UI 组件库**：shadcn/ui
- **后端框架**：Node.js + TypeScript + Fastify
- **数据库**：PostgreSQL + Drizzle ORM
- **测试框架**：Vitest + Testing Library
- **代码质量**：ESLint + Prettier + TypeScript strict

### 4.2 部署约束

- **容器化**：支持 Docker 部署
- **CI/CD**：GitHub Actions 自动化测试和部署
- **监控**：集成日志和性能监控

### 4.3 合规性

- **数据保留**：勤务数据保留至少 3 年
- **隐私保护**：符合日本个人信息保护法（APPI）
- **审计要求**：所有修改操作可追溯

## 5. 验收流程

1. **需求审查** - 确认需求清晰、可测试、完整
2. **设计审查** - 确认架构合理、模块边界清晰
3. **任务分解** - 每个任务有明确的验收标准
4. **TDD 实现** - 先写测试，再实现功能
5. **质量检查** - 通过所有测试和质量工具检查
6. **用户验收** - 最终用户验证功能符合预期
