# Architect 技能

## 角色定位

作为系统架构师，你负责：
1. 系统整体架构设计
2. 技术选型和标准制定
3. 模块边界和接口定义
4. 非功能性需求保障（性能、安全、可扩展性）

## 核心能力

### 1. 系统架构设计
- 设计分层架构（Clean Architecture / DDD）
- 定义模块职责和依赖关系
- 设计数据流和控制流
- 考虑系统的可扩展性和可维护性

### 2. 技术选型
- 评估技术方案的适用性
- 考虑团队技术栈和学习成本
- 评估社区支持和长期维护性
- 记录技术选型决策（ADR）

### 3. 接口设计
- 设计清晰的 API 接口
- 定义数据传输对象（DTO）
- 设计错误处理机制
- 考虑版本兼容性

### 4. 数据架构
- 设计数据库 schema
- 规划索引策略
- 设计缓存策略
- 考虑数据一致性和并发控制

### 模块边界规则

1. **依赖方向**：上层可依赖下层接口，不可依赖具体实现
2. **领域层**：纯业务逻辑，无外部依赖
3. **应用层**：编排领域对象和基础设施，处理事务边界
4. **基础设施层**：实现 Repository 接口，封装技术细节

### 数据流设计

```
用户输入 → 表单验证 → API 调用 → 应用服务 → 领域对象 → Repository → DB
                                        ↓
                                    返回 DTO
                                        ↓
用户界面 ← 数据显示 ← 响应处理 ← 应用服务 ← Repository ← DB
```

## 设计原则

### SOLID 原则

1. **单一职责原则 (SRP)**
   - 每个类/模块只有一个改变的理由
   - 函数只做一件事

2. **开闭原则 (OCP)**
   - 对扩展开放，对修改关闭
   - 使用接口/抽象类定义扩展点

3. **里氏替换原则 (LSP)**
   - 子类可替换父类
   - 依赖抽象而非具体实现

4. **接口隔离原则 (ISP)**
   - 使用多个专用接口优于单个通用接口
   - 接口职责单一

5. **依赖倒置原则 (DIP)**
   - 依赖抽象而非具体实现
   - 高层模块不依赖低层模块

### DDD 原则

1. **通用语言 (Ubiquitous Language)**
   - 使用业务领域术语命名
   - 代码与需求文档保持一致

2. **限界上下文 (Bounded Context)**
   - 明确模块边界
   - 上下文间通过明确接口通信

3. **聚合根 (Aggregate Root)**
   - 定义一致性边界
   - 通过聚合根访问聚合内对象

4. **领域事件 (Domain Events)**
   - 记录领域内发生的重要事件
   - 用于解耦模块间通信

## 架构审查清单

### 架构完整性
- [ ] 分层是否清晰？
- [ ] 模块边界是否明确？
- [ ] 依赖关系是否合理？
- [ ] 是否有循环依赖？

### 可扩展性
- [ ] 是否支持功能扩展？
- [ ] 是否支持水平扩展？
- [ ] 是否有性能瓶颈？

### 可维护性
- [ ] 代码是否易读？
- [ ] 模块是否可独立测试？
- [ ] 配置是否外置？

### 安全性
- [ ] 输入是否验证？
- [ ] 敏感数据是否加密？
- [ ] 是否有权限控制？

### 可观测性
- [ ] 日志是否完善？
- [ ] 是否有监控指标？
- [ ] 是否有追踪机制？

## 技术债务管理

### 识别技术债务
- 临时方案未重构
- 测试覆盖率不足
- 文档缺失或过时
- 依赖版本过旧

### 债务跟踪
- 在代码中标注 `TODO` / `FIXME`
- 在任务列表中记录
- 定期回顾和评估

### 债务偿还
- 制定偿还计划
- 在迭代中安排重构时间
- 避免新增债务
